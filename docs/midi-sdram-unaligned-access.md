# MIDI HardFault on Note-Off (Advance / SDRAM unaligned access)

## Summary

After the SDRAM memory refactor (commits `20a931b5` and `2a5c265a`) and the
configurable phrase length merge, MIDI instruments started hard-faulting on
note-off on the Advance hardware. The crash is column-specific in a very
particular way:

- Song columns 1 and 5 (0-indexed channels `0` and `4`) work.
- Song columns 2, 3, 4, 6, 7, 8 (0-indexed channels `1, 2, 3, 5, 6, 7`) crash
  the instant the note is released.
- The crash only affects MIDI instruments. Sample instruments are fine on
  every column.
- Holding an auditioned MIDI note is fine; releasing it faults. During
  phrase playback the first note plays, then the implicit note-off on the
  next step triggers the fault.

The pattern is "every channel where `c * 5` is a multiple of 4 works, every
other channel hard-faults", and that is exactly what the root cause produces.

## Root Cause

`MidiInstrument` stores per-channel chord state as:

```cpp
etl::array<uint8_t, MAX_MIDI_CHORD_NOTES + 1> lastNotes_[SONG_CHANNEL_COUNT];
```

`MAX_MIDI_CHORD_NOTES + 1 == 5`. `etl::array<uint8_t, 5>` is a 5-byte struct
with `alignof == 1` (it is just `uint8_t _buffer[5]`), so the array of 8 of
them is packed and each per-channel entry sits at offset `c * 5` from the
start of the field:

| c | offset | 4-byte aligned? |
| - | ------ | --------------- |
| 0 | 0      | yes             |
| 1 | 5      | no              |
| 2 | 10     | no              |
| 3 | 15     | no              |
| 4 | 20     | yes             |
| 5 | 25     | no              |
| 6 | 30     | no              |
| 7 | 35     | no              |

That table is the "channels 0 and 4 work" pattern.

### Why alignment matters now but did not before

Before the memory refactor, `InstrumentBank` was an embedded member of
`Project`, which lived in normal internal SRAM. ARM Cortex-M7 permits
unaligned `LDR/STR` to Normal memory, so the 5-byte stride was harmless.

After `2a5c265a`, `InstrumentBank` is placement-new'd into an SDRAM-backed
buffer:

```cpp
ADV_SECTION_INSTRUMENT_BANK static char
    instrumentBankBuf[sizeof(InstrumentBank)];
```

That section is linked into `SDRAM1`, which the linker script places at
`ORIGIN = 0xC0000000`. On ARMv7-M the default memory map marks
`0xA0000000-0xDFFFFFFF` as Device-shareable. Without an MPU region that
remaps the SDRAM range to Normal/cacheable memory, every unaligned word
access in SDRAM raises a UsageFault, which (on this firmware) escalates to
a HardFault.

### Why hold works and release crashes

`MidiInstrument::Start` and `MidiInstrument::Render` only touch individual
bytes of `lastNotes_` and `first_`, so the compiler emits `LDRB/STRB`,
which are alignment-safe even on Device memory.

`MidiInstrument::Stop` is different:

```cpp
void MidiInstrument::Stop(int c) {
  ...
  for (int i = 0; i < MAX_MIDI_CHORD_NOTES + 1; i++) {
    if (lastNotes_[c][i] == 0) continue;
    ...
    svc_->QueueMessage(msg);
  }
  lastNotes_[c].fill(0);   // <-- the fault site
  playing_ = false;
}
```

GCC will happily lower a 5-byte zero fill to `STR #0; STRB #0` (one 32-bit
store plus one byte store). The 32-bit store goes to `&lastNotes_[c][0]`,
i.e. `base + c * 5`. For `c == 0` or `c == 4` that address is 4-byte
aligned and the write succeeds. For every other `c` the address is
unaligned, and on Device-typed SDRAM the CPU raises a UsageFault -> HardFault.

The release path is hit from two places:

- `PhraseView::stopAudition` -> `Player::Stop` -> `PlayerChannel::StopInstrument`
  -> `MidiInstrument::Stop` (releasing an audition).
- `Player::playCursorPosition` calling `mixer_.StopInstrument(channel)` on
  every new note or `NOTE_OFF` step during phrase playback.

Both flows end in the same `fill(0)` call, which is why "release after
audition" and "next note in a phrase" both fault.

### Why sample instruments are unaffected

`SampleInstrument` keeps its per-channel state outside SDRAM:

```cpp
__attribute__((section(".DTCMRAM"))) static struct renderParams
    renderParams_[SONG_CHANNEL_COUNT];

static signed char lastMidiNote_[SONG_CHANNEL_COUNT];
static fixed lastSample_[SONG_CHANNEL_COUNT][2];
```

`renderParams_` is forced into DTCM and the rest are file-static (BSS in
normal internal SRAM). They are also sized in multiples of 4 bytes per
channel, so even if they were in SDRAM there would be no unaligned access.
Sample playback never touches the offending memory region with an
unaligned access, which is why every column works for samples.

## Confirming the fault

If you reproduce the crash under a debugger, the fault flags will show:

- `SCB->CFSR.UFSR.UNALIGNED` set.
- Faulting PC inside `MidiInstrument::Stop`, on the store generated by
  `lastNotes_[c].fill(0)`.
- `BFAR` / faulting address of the form `0xC0xxxxxx + 5 * c`, where `c` is
  the offending song channel.

## Fix options

There are four reasonable ways to address this. They are listed roughly in
order from "proper fix" to "narrow workaround".

### Option 1: Configure the MPU to mark SDRAM as Normal memory

The correct long-term fix. Add an MPU region at boot (after FMC is up,
before any SDRAM access) that covers the SDRAM1 range and marks it as
Normal, Inner/Outer write-back, write-allocate, shareable as required.
This:

- Allows unaligned access (so the bug disappears).
- Lets the D-cache cache SDRAM, which is a large performance win.
- Removes a whole class of latent bugs anywhere else that the firmware
  touches SDRAM-resident data.

Cost: requires careful MPU/cache configuration and cache-maintenance
discipline for any DMA into/out of SDRAM.

### Option 2: Align the MIDI per-channel buffers (currently applied)

Force every `lastNotes_[c]` onto a 4-byte boundary so the compiler can
never generate an unaligned word access against it:

```cpp
alignas(4) etl::array<uint8_t, 8> lastNotes_[SONG_CHANNEL_COUNT];
```

The element size goes from 5 to 8 (a multiple of 4), so each per-channel
entry is naturally aligned, and the explicit `alignas(4)` keeps the field
itself aligned even if neighbouring members ever change. The extra 3
padding bytes per channel (24 bytes total) are never read or written
explicitly; `fill(0)` simply clears all 8 bytes, which is harmless because
the loop bound `MAX_MIDI_CHORD_NOTES + 1` (= 5) still controls how many
MIDI messages get queued.

Pros: one-line, no behavioural change, immediately ships MIDI on every
column.

Cons: it is a localised fix. Anything else added later that touches an
unaligned field of an SDRAM-resident object can resurrect the same fault.

### Option 3: Replace `fill(0)` with an explicit byte loop

Avoid the compiler-generated word store entirely:

```cpp
for (int i = 0; i <= MAX_MIDI_CHORD_NOTES; ++i) lastNotes_[c][i] = 0;
```

You would then also have to audit every other access into MidiInstrument
(and any other SDRAM-resident object) for implicit word accesses
(`memcpy`, struct assignment, `memset`, `etl::fill`, etc.). It is the most
fragile of the four options and is not recommended on its own.

### Option 4: Keep MidiInstrument out of SDRAM

Either move `InstrumentBank` (or just the MIDI pool) back to internal
SRAM, or split the bank so only the bulk pools live in SDRAM. This
sidesteps the alignment issue but partially defeats the point of the
memory refactor and may not be possible once instrument counts grow.

## Recommendation

Ship Option 2 now to unblock MIDI on every column, and follow up with
Option 1 (MPU + cache configuration for SDRAM) so the underlying class of
bug cannot reappear and so the firmware actually benefits from the D-cache
when working out of SDRAM.
